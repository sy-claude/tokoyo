# 10 マイルストーン（milestones）v1.0

**この文書でできること**
- ゲームを25回の作業（マイルストーン＝M）に分け、各回で「何を読み、何を作り、何ができたら完了か」を決めます。
- 各回の終わりに、依頼者がスマホで何を試し、何を選べばよいかが分かります（PR本文にそのまま載ります）。
- 遊んだ感想を、次の回の指示や「数値だけの調整」にどう変えるかを決めます（末尾）。

**関連文書**：00_core（全体）／decisions（D46）／01〜09 の各「受け入れ基準」「依頼者が実機で確かめること」／09 §11（テスト基盤）・§12.3（PR・PROGRESS）。CLAUDE.md と PROMPTS.md の指示文は本書の各Mの節（`§M3a` の形）を参照する（各Mの「読む文書と節」が索引を兼ねる）。

## 4. 全Mに共通の約束

### 4.1 セッションの手順
1. 読む：CLAUDE.md → PROGRESS.md → 本書 §0・§4 と担当Mの節 → 担当Mの「読む文書と節」。00_core は §0・§2・§4・§12 だけ（M0a のみ全体）。列挙に無い節が必要になったら、まずキー名や見出しを `grep` して該当部分だけ読む。文書全体を読まない。
2. `npm ci`（node_modules が無いとき）。`/opt/pw-browsers/STATUS` を見て e2e の可否を知る。
3. 前回の PROGRESS「次」「既知の問題」と、指示文の末尾にある依頼者の感想（§感想の受け取り方）を先に処理する。
4. 実装 → 単体テスト → e2e → リプレイ → shots の順。受け入れ基準は番号の小さい順が優先。
5. 終わり方：`npm run verify`（Bash timeout 600000ms）→ PROGRESS.md 更新 → commit → push → 最終メッセージに PR の題名と本文（09 §12.3）。

### 4.2 完了の条件（全Mに共通。各Mの受け入れ基準に加えて）
1. `npm run verify` が成功。ブラウザが無いときは `verify:fast` 成功＋`E2E SKIPPED` を PROGRESS の既知の問題に書き、push 後に CI の結果を確かめる（09 §11.4）。
2. 前のMまでの全テストと全リプレイが通る。リプレイのハッシュが変わったら原因を特定し、意図した変更のときだけ `npm run replays:update`（PR に「リプレイ更新：理由」）。
3. このMのリプレイを1本以上足す（`tests/replays/src/<m>_<名>.js`、このMの機能を使う60〜600tick）。
4. shots 8枚（§4.8）を撮り、`sheet.png`・`sheet_gray.png` を見て、各Mの「見るべき点」の合否を PROGRESS に1行ずつ書く。
5. コンソールのエラー0件。不変条件の検査群（09 §2）が通る。
6. **期待値の書き方**：テストの期待値は config・data から計算する（例：頂点の高さは `cfg.movement.jumpHeightM`±0.02）。式で導けない検算値（例：走り跳び3.90m、DPS19.5）はテスト名の先頭に `[検算]` を付け、横に出典（`// 02受7`）を書く。調整セッションでは `[検算]` の期待値だけ更新してよい。
7. PR本文の「依頼者が試すこと」は各Mの欄をそのまま使い、公開URL（`git remote` の持ち主から `https://<持ち主>.github.io/<repo>/`）を先頭に書く。「依頼者に判断を求める点」があれば PR本文の末尾に選択肢と AI の推奨を付けて書く。
8. **時間切れ**：満たした基準の番号と残りを PROGRESS「次」に書き、verify が通る状態で push する。次のセッションは「§M3a の続き」として始める（新しいMに進まない）。

## 感想の受け取り方（依頼者の感想 → 次の指示・調整）

### 1. 流れ
1. 依頼者は PR の「依頼者が試すこと」を試し、感じたことを普段の言葉で書く（数値は不要）。「判断を求める点」には「A」「推奨で」の形で答える。
2. 感想は**次のMの指示文の末尾**に下の形で貼る。手触りの感想だけで直したいときは、次のMの前に「調整だけのセッション」（§5）をはさむ。M2.5（符）と M3b（手応え）の後は、調整セッションをはさむのを既定とする。
```
## 前回の感想（M2b）
- カメラが近くて酔う
- 回避のあと、すぐ攻撃できない
## 判断
- M2b カメラの距離：B
- M2b 自動の回り込み：推奨で
```
3. AI はセッションの最初（§4.1-3）に感想を分類し、処理した結果を PROGRESS.md の「済み」に `感想：〇〇 → キー △△ を x→y` の形で書く。PR本文の要約にも1行入れる。

### 2. 分類と扱い
| 種類 | 見分け方 | 扱い |
|---|---|---|
| 不具合 | 動かない・止まる・落ちる・表示が欠ける・音が出ない | 再現するテストを先に書いてから直す。30分で直らない見込みなら PROGRESS の既知の問題へ（再現手順・影響・対処予定） |
| 手触り | 遅い・速い・重い・軽い・届かない・酔う・強い・弱い | §3 の表でキーを特定し、config の値だけを変える。1回の変更幅は ±10〜20%（ConfigEntry の min/max の内側）。§4 の「地図に響く値」は条件付き |
| 見た目・音の好み | 地味・赤すぎ・うるさい・見にくい | `palette`・`render`・`audio` の値の範囲で。色の役割（00 §1.2）と明度の三層を破る変更はしない（白黒版の shots で確認） |
| 設計の変更 | 新しい操作・敵・規則・画面の追加 | 実装しない。PROGRESS「依頼者に聞くこと」に、影響（decisions の影響範囲）と案を書いて設計者に回す |
| 判断の答え | 「A」「推奨で」 | そのとおりに反映し、`docs/decisions.md` の「依頼者の決定」に U番号で1行追記（例「U7 カメラ距離4.5m（M2b の判断）」） |
| 曖昧 | 「なんか違う」 | 該当Mの「依頼者に判断を求める点」と同じ形の選択肢（A/B/C と推奨）を作り、PR本文で聞き返す。推測で大きく変えない |

### 5. 調整だけのセッション（Sonnet で config の値だけを変える）
- **使うとき**：感想が「手触り」「見た目・音の好み」だけのとき。新しいMの前に1回、10〜20分。
- **ブランチ・PR**：`claude/tune-<M>-<連番>`（例 `claude/tune-m2b-1`）、題名「調整: M2b カメラの距離」。
- **してよいこと**：`src/config/*.js` の値（ConfigEntry の min/max の内側）、感想の対象の技・敵に限った `src/data/*.js` の数値、`[検算]` テストの期待値、`npm run replays:update`（PR に理由）、PROGRESS.md と decisions の追記。
- **してはいけないこと**：`src/config` と `src/data` 以外のコードの変更、キーの追加・削除、設計書の数値の書き換え（設計書と違う値にしたら PROGRESS の「設計との差分」に `キー：設計値→現在値（理由・日付）` を残す）。
- **手順**：① PROGRESS.md と本節を読む ② 感想ごとに §3 でキーを決める（§4 に当たれば条件を確かめる）③ 値を変える ④ `npm run verify:fast` → 落ちたら `[検算]` だけ直す（他が落ちたら変更を戻して報告）⑤ PROGRESS 更新 → commit → push → PR本文（変えたキーの表と「依頼者が試すこと」2〜3行）。
- **指示文の型**（PROMPTS.md にそのまま置く）：
```
調整だけのセッションです。docs/10_milestones.md の「感想の受け取り方」§3〜§5 に従い、
src/config と src/data の値だけを変えてください。コードは変えないでください。
## 感想（M○○）
- （ここに感想を箇条書き）
最後に、変えたキー（前→後）の表と、スマホで試すこと2〜3行を PR本文として書いてください。
```
- **依頼者が自分で値を探す場合**：URL に `?debug=1` を付け、調整パネルのスライダーで好みの値を探し、「JSONをコピー」した文字列を上の指示文の感想の下に貼る。AI はその値をそのまま config に写す（§4 の条件は同じ）。
